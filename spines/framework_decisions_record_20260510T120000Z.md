# Framework Decisions Record

**Status:** Working artifact, instantiated 2026-05-07. Hash-chained record of architecture decisions and design rationale. Each entry uses AAR substrate (intent / outcome / why / lessons / skills) plus three integrity fields (timestamp, prior_entry_hash, this_entry_hash). The hash chain provides tamper-evidence and chain-of-custody portability across platforms.

**What this is:** The records-keeping discipline applied to the framework's own design evolution. Distinct from `cohort_temporal_record.md` (which captures cohort and operational records) and from handoff documents (which capture session-by-session continuity). This artifact captures *why* design decisions were made, with verifiable provenance back to the genesis entry.

**What this is not:** A handoff replacement. Handoffs continue to serve session-to-session continuity and current-state-of-work. This record is for design rationale specifically — the kind of content that needs to remain authentically tied to predecessor context across years and across the platforms a future framework operator may use.

**Why hash-chained:** Per Dan's design specification (records-keeping audit Q6 answer): "some hash of the authenticity to show a given record is authentically tied to the previous is useful... we want an architecture which can regularly evaluate the full record against what a given perspective may say in the moment and provide some input on how to refine that toward business objectives." The hash chain addresses authenticity. The "evaluate against current perspective" capability lives with the agent reading the file, not in the format itself.

---

## Hash Protocol

**Hash function:** SHA-256.

**Per-entry computation:** Each entry's `this_entry_hash` is the SHA-256 hex digest of the UTF-8 encoded concatenation: `timestamp + "|" + intent + "|" + outcome + "|" + why + "|" + lessons + "|" + skills + "|" + prior_entry_hash`.

**Chain construction:** Each entry's `prior_entry_hash` field is the prior entry's `this_entry_hash`. The genesis entry's `prior_entry_hash` is sixty-four zeros (`0000...0000`) as the chain sentinel.

**Verification:** A reader can verify the chain by recomputing each entry's hash from its content and prior_hash, then checking that the recomputed value matches the recorded `this_entry_hash` and that the next entry's `prior_entry_hash` equals this entry's `this_entry_hash`. Any mismatch indicates the entry has been modified after recording, an entry has been inserted or deleted, or the chain has been broken.

**Tooling:** A small verification script can compute the chain from the file's structured fields. The chain is independent of the surrounding markdown formatting — only the AAR-substrate fields and the prior-hash are inputs.

**Limitations:** This is a tamper-evidence chain, not a tamper-prevention mechanism. A bad actor with write access can recompute the entire chain after editing earlier entries. The chain's value lies in detecting unintentional drift, copy-paste corruption across platforms, or out-of-order edits — and in producing a record that's portable across platforms in a way that proves itself rather than relying on platform-level trust.

## Append protocol

When a new design decision warrants recording:

1. Compose the AAR-substrate fields (intent, outcome, why, lessons, skills). Keep each field substantive but concise — this artifact is for design rationale, not implementation detail.
2. Set `timestamp` to ISO 8601 with timezone offset (per the existing entries).
3. Set `prior_entry_hash` to the most recent entry's `this_entry_hash` (the last hex string above this section).
4. Compute `this_entry_hash` as SHA-256 over `timestamp + "|" + intent + "|" + outcome + "|" + why + "|" + lessons + "|" + skills + "|" + prior_entry_hash` (UTF-8 encoded).
5. Append the new entry to the Entries section above this protocol section, preserving chronological order.
6. The append protocol section moves to remain at the file's end after the most recent entry.

A small Python script for the hash computation:

```python
import hashlib
content = timestamp + "|" + intent + "|" + outcome + "|" + why + "|" + lessons + "|" + skills + "|" + prior_entry_hash
this_entry_hash = hashlib.sha256(content.encode("utf-8")).hexdigest()
```

The chain remains valid as long as no entry's content is modified after recording. If a correction is needed, the correction is appended as a new entry referencing the original by hash, not by editing the original entry. This preserves the chain's integrity at the cost of leaving incorrect content in the historical record — which is consistent with the framework's records-keeping discipline (capture rather than smooth; the historical state is part of what the record captures).

## Verification protocol

Hash-chain integrity (verified per-entry by the Hash Protocol above) is one verification layer; outcome verification is another. The hash chain catches direct tampering with entry contents but cannot catch outcome claims that don't match the actual state of the files cited. The two layers are complementary.

**Why outcome verification matters.** Entry outcome claims describe what was changed in which files. Those claims should match reality. Bulk-claim-outcome entries (entries that cover multiple component changes across multiple files in a single batch) are particularly prone to overclaiming on small touches while the substantive work gets done correctly — verification surfaced three residuals in Entry 1 alone (D1 filename fix, README reading order update, glossary entries) before this protocol was formalized.

**Cadence.** At every fifth entry (Entry 5, 10, 15, ...), verify the outcome claims of the prior five entries against the actual state of the files cited. The first verification window runs at Entry 5, covering Entries 1–5. The next runs at Entry 10, covering Entries 6–10. And so on.

**What to verify.** For each entry's outcome field, identify the discrete claims (e.g., "principle #X added to file Y," "section Z added to file W," "new file V created"). For each claim:
- Does the cited content exist where the claim says?
- Does the cited file exist if it was claimed to be created?
- Are filename references correct?
- Are cross-references that would need updating actually updated?

**What happens when verification finds residuals.** Per the chain Append protocol, prior entries are not edited. Residuals are fixed in a new entry that explicitly captures both the correction and the original entry's overclaim. The new entry's outcome explicitly notes which prior entry's claim was the source of the residual; this preserves the historical record while updating going-forward state. The pattern matches the timestamp-correction pattern from Entry 4 — capture the drift, fix forward, preserve the originals.

**What happens when verification finds nothing.** No new entry needed; verification can be noted as a Change Log row in `cohort_temporal_record.md` (e.g., "Verification pass over Entries N through N+4: all outcome claims confirmed").

**Implementation.** Verification can be partially automated (grep against cited file paths and content patterns) and partially manual (judgment about whether a section's content actually delivers what the entry's outcome claims). The `verify_chain.py` script handles hash integrity; an analogous `verify_outcomes.py` could handle outcome verification. Building it is deferred until the cadence is exercised enough to know what patterns are worth automating.

**Retroactive verification of prior windows.** When a verification pass re-examines a prior window (because the framework gains a new window-completion mechanism, because an audit triggers a re-pass, or because a stakeholder requests one), the re-examination requires a fresh grep against current file state. A previous-session verification report that pronounced a window clean is itself an unverified data point; treating it as ground truth substitutes claim-to-have-already-checked for actual verification. The compound-overclaim pattern surfaced during the 2026-05-07 evening session demonstrates the failure mode: an Entry-7 claim that Window 1 (Entries 1–5) had been retroactively verified clean was carried forward in subsequent work as if Window 1 were settled, when in fact several Window-1 outcome claims still had residuals. Fresh-grep requirement closes this gap. The intake-skepticism principle (operating constraint #6) applies here too: the agent's own prior verification claims are intake that requires skepticism, not testimony that bypasses it. *Forward-ported as Entry 14 from orphan-Entry 11 on the divergent 20260507_evening track; original orphan-chain context: SHA-256 chain head `03e76a5b92c000f5d5ef412954d41baf2bf573fcab7770d005b109357205ddf2` (orphan-Entry 11).*

**Composition-time discipline.** When composing a chain entry's outcome field, the agent runs grep against current file state for each discrete claim before writing the outcome (per operating constraint #9 in `core_principles_for_agent_behavior.md` — this subsection is the records-side mirror). Composition-time grep is the *first* verification layer; cadence (above) is the second; retroactive verification of prior windows (above) is the third. The three layers are complementary: composition-time prevents the failure mode at its source, cadence catches anything composition-time missed within a bounded window, retroactive catches drift between cadence windows. The compound-overclaim pattern surfaced repeatedly across Entries 1, 5, 9, 12 demonstrated that the protocol's prior two-layer architecture left a gap at the composition level — entries authored from intent rather than from grep evidence consistently overclaimed on small-file edits while substantive work landed correctly. Composition-time discipline closes that gap structurally. *Forward-ported as Entry 15 from orphan-Entry 12 on the divergent 20260507_evening track; original orphan-chain context: SHA-256 chain head `4db79acebb556138f426cbbc2ee3b5f967606ec7aa01b22a7b0cdf8bddfa5324` (orphan-Entry 12).*

**Cadence patterns at multiple scales.** Chain-entry verification cadence and major-patch handoff cadence are coupled, with both operating on accumulated effort rather than entry count. Each entry self-tags an effort estimate at composition time on a 1/3/5 scale (Small / Medium / Large) — small enough that estimation is fast, large enough that the tags differentiate. Composition-time effort tagging doubles as a sanity check against the small-inline-edits-overclaim pattern: if an entry's intent suggests M but the outcome covers more than three discrete file changes, the L tag is more honest. Major-patch handoff threshold is 15 accumulated effort units since the last major-patch handoff (calibrated empirically over the first few cycles). Hybrid ceiling: every 10 entries triggers a major-patch handoff regardless of accumulated effort, to prevent indefinite deferral if entry composition keeps tagging S. **Claim-versus-record divergence detection.** When a stakeholder claim arrives that the records cover (about a person, event, framework detail, or historical fact), the agent runs an observe-and-compare check between the claim and current record state before integrating the claim. The four layers together form the protocol's complete coverage: composition-time prevents source-level overclaim; cadence catches anything composition-time missed within a bounded window; retroactive catches drift between cadence windows; claim-versus-record divergence catches mismatch at intake time when new claims would otherwise overwrite or silently disagree with existing records. **Post-commit verification routine.** Chain entries that produce canonical-state file changes ship with a `verify_entry_N.py` script the stakeholder (or next session) runs after the file changes are applied to project knowledge. Pattern established by `verify_entry_17.py`. The routine verifies (a) presence of all anchor strings the entry's outcome claims (substring or regex matches against cited file paths), and (b) chain integrity by parsing the entry's AAR fields from the canonical file, recomputing the SHA-256 hash from the field concatenation, and comparing to the recorded `this_entry_hash`. PASS/FAIL output is the canonical post-commit signal. This is the *fifth* verification layer alongside composition-time (1st), cadence (2nd), retroactive (3rd), and claim-versus-record divergence detection (4th). The structural gap this layer closes is between agent composition-time verification (operates against working state — the agent's intra-session file modifications) and post-commit canonical state (what landed in project knowledge after the stakeholder applies the file replacements). This is a double-loop response (per the Argyris/Schön frame) to the recurring multi-file-outcome overclaim pattern (Entries 1, 5, 12, 14, 16): composition-time discipline alone is necessary but insufficient for chain integrity, and the recurring pattern after composition-time strengthening is signal that the gap requires a new layer rather than another tightening of the existing layers. The discipline is part of the cross-session handshake protocol documented in `README.md`. *Codified as Entry 18; pattern instantiated by `verify_entry_17.py` per Entry 17 outcome.* Hardened in Entry 19 with the **hash-manifest discipline**: each chain entry that produces canonical-state file changes captures the SHA-256 of each produced file at composition time and embeds the hashes as an `EXPECTED_HASHES` dict at the top of `verify_entry_N.py`; the handoff document mirrors the same manifest in human-readable form. The hash check runs first (definitive byte-equality against expected manifest) and content-pattern checks remain as the diagnostic layer surfaced by hash mismatch. Hash check closes a composition-time-drift mode that content-pattern verification alone cannot catch — where the verify script and handoff both reflect the same composition-time understanding and can be wrong in the same direction; mechanical linkage via composition-time hashing means all three artifacts (produced files, handoff manifest, verify EXPECTED_HASHES) derive from one fingerprint and any divergence is mechanical. The hash-manifest discipline parallels the hash-chain integrity discipline in use for entries since genesis: both use hash-mechanical linkage to close drift between authoritative-at-time content and downstream artifacts. Hash check is necessary but not sufficient — content-pattern checks catch outcome-correctness mismatches that hashes don't surface (e.g. Claude composes a wrong file consistently across all three artifacts). Verify routine ordering is hash-first (definitive), content-patterns-second (diagnostic), chain-integrity-third (authentication). *Codified as Entry 19; first canonical instance is `verify_entry_19.py`; motivated by seventh-instance recurrence of the multi-file-outcome overclaim pattern on `cohort_temporal_record.md` across Entries 17, 18, and 19.* Hardened further in Entry 20 with the **modification-confirmation discipline**: each chain entry that produces canonical-state file changes also captures the SHA-256 of each modified file *as observed in canonical state before modification* and embeds those hashes as a `PRIOR_HASHES` dict at the top of `verify_entry_N.py` alongside `EXPECTED_HASHES`. The verify routine runs a Layer 0 inequality check first (`PRIOR_HASHES[F] ≠ EXPECTED_HASHES[F]` for every claimed-modified `F`) before any other layer. This closes the composition-layer no-write fabrication mode that the hash-manifest discipline alone cannot catch — hash-manifest catches "produced file didn't land in canonical state" (transmission-layer drift); modification-confirmation catches "claim of modification with no actual delta produced" (composition-layer no-write). The two disciplines together form complete coverage of the modification-claim verification space: composition-time (Layer 0: PRIOR ≠ EXPECTED) catches no-write fabrication; post-commit hash-manifest (Layer 1: produced equals EXPECTED) catches transmission drift; content-pattern checks (Layer 2) remain as diagnostic surface; chain-integrity check (Layer 3) authenticates the entry. The taxonomy refinement is significant: Entries 17 and 18 actually exhibited composition-layer no-write on `cohort_temporal_record.md` (claims of modification without produced delta — the third-attempt closure in Entry 19 was effectively the first time the file was actually composed correctly), whereas Entry 19 exhibited transmission-layer drift on the same file (correctly produced but not landed in canonical). The modification-confirmation discipline retroactively explains why Entry 19's hash-manifest discipline was necessary-but-not-sufficient and what additional structural response closes the remaining gap. The discipline is the *third* instance of hash-mechanical linkage as the structural response when content-pattern verification has architectural limits (chain integrity since genesis; post-commit hash-manifest in Entry 19; modification-confirmation in Entry 20), suggesting hash-mechanical linkage is a recursively-applicable framework-level pattern. *Codified as Entry 20; first canonical instance is `verify_entry_20.py`; motivated by stakeholder structural review surfacing the directional gap in Entry 19's hash-manifest discipline, in the context of the eighth-instance recurrence of the multi-file-outcome overclaim pattern (fourth consecutive instance on `cohort_temporal_record.md` — Entry 19's produced file did not land canonically and Entry 20 is the fourth-attempt closure of canonical landing).* Hardened further still in Entry 23 with the **rename-as-navigation discipline** as the response when the verification layers persistently detect a transit failure on a specific file across multiple entries despite correct production.
